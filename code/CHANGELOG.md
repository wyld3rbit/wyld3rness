# Changelog

Notable changes to wyld3rness and its example app. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions will follow [Semantic Versioning](https://semver.org/) once releases begin. Each entry links the decision record that explains it.

## Unreleased

### Direction

- **Autonomous operation, with cost as an invariant.** The target is on-call without a human approving each action: an act, verify and undo loop on a simulated production, a budget per incident and cost per resolved incident. The order of the four planned controls is kept, human approval moves from each action to each kind of action, and the planned computed escalation signal and harder static golden set are replaced by a recovery check and versioned faults. The loop is built and acts only on the simulated production; the budget, the policy and the credential are planned, and the design, the visualizer and the README show which is which. ([ADR 0008](docs/adr/0008-autonomous-operation-with-cost-as-an-invariant.md))

### Harness

- **Eval gate.** Runs an app on golden cases with known answers. Labels such as severity are matched exactly, and a judge model scores faithfulness, response relevancy, context recall and action quality. Each run is compared with a frozen baseline, with seeded bootstrap intervals, and fails on a measured regression or a judge failure rate above its cap. A negative control can never become a baseline. ([ADR 0005](docs/adr/0005-gate-releases-on-measured-answer-quality.md))
- **One interface for any app.** `SystemUnderTest` (`describe`, `answer`, `summarise`) separates the harness from the app. A test fails if the harness imports anything but the standard library, its declared dependencies and itself. ([ADR 0006](docs/adr/0006-eval-gate-as-harness-component-attested-in-ci.md))
- **Attested CI gate.** A full, clean, passing run writes an attestation: the hash of every answer-affecting file, found from the eval's import closure plus declared data, lock and compose files. CI recomputes the hashes in its own job and fails a change no passing run covers. ([ADR 0006](docs/adr/0006-eval-gate-as-harness-component-attested-in-ci.md))
- **Eval gate at every commit.** The pre-commit hook exports exactly the staged tree, gives it its own environment, refuses an import that escapes it, runs the eval gate there and adds the attestation to the same commit; a failed gate refuses the commit. A case whose judge inputs (question, reference, contexts, answer, proposed action, judge model and digest, prompts, judge code, embedder, lock) are identical to the attested run's keeps that run's score, which it names; `--no-reuse` judges every case. The pre-push hook checks each pushed commit's attestation, which merges and rebases would otherwise skip. `git commit <path>` is refused. This ends the old deadlock: an attested file could not be committed, because the gate refused an uncommitted tree. (`code/src/wyld3rness/eval/staged.py`, `reuse.py`)
- **The loop.** `wyld3rness.loop` runs one incident with no person approving each action: an app's `Environment` (observe, apply an action and get back its undo, the user stream, the clock) and a `Decider` (the model behind its own validation) go in; at most 3 tries of 1 or 2 actions come out, each applied, waited on, verified and held, then kept, or undone last first and retried with what failed. Every other path (out of tries, an invalid decision, an action not carried out, a failed undo, an action with no undo that did not resolve it, an error) ends in the safe state, which puts back what can be put back and changes nothing else. The verdict is the good-second rule the storm controls were scored on, moved from simprod's checker unchanged; re-scoring the 63 control runs with the moved code changed none of their 252 verdicts. Fakes for both ports in `wyld3rness.testing`. Not yet in front of it: policy, credential, budget. (research log, entry 013)
- **Policy and budget in the loop.** The policy is a table an app declares as data (allowed kinds, which must be alone, a precondition read from live state); the loop checks the whole decision before applying any of it, and a refused decision applies nothing and spends a try. The budget reserves each model call's worst case before it runs (the prompt's bytes bound its input tokens, a cap its output) and refuses an unpriced model or a call that does not fit; either refusal ends in the safe state. (research log, entry 014; ADR 0008, step 4)
- **A credential for every action.** The loop signs each action and undo just before sending it: one action with its exact arguments, valid 60 s, usable once. OpenBao's Transit engine signs, so the key never leaves the vault and the agent holds nothing that can sign; an action that cannot be signed is not sent. (research log, entry 015; ADR 0008, step 4)
- **Injection suite.** `wyld3rness.loop.injection`: attacks, goals, `run_attack` through a decider and the policy, and `Fooled`, the worst a model can do. (ADR 0008, step 5)
- **The loop, traced.** `wyld3rness.loop.traced` wraps the loop's four ports so every observation, decision, policy check, signature, action and wait is a span inside the incident's trace, and each model call the decider reports is a generation; a credential never reaches a span. The remote decider now returns each decision's reason and model calls with its answer, and `CommandTrace` exposes its trace id. (ADR 0008, step 6)
- **A script baseline and the experiment's statistics.** `wyld3rness.loop.script.Scripted` proposes fixed sets of actions in a given order, one per try, through the same loop as a model, so a model must beat it to earn its place. `wyld3rness.loop.experiment`: a paired difference with a seeded bootstrap interval, the exact paired sign test, a step-down correction for multiple comparisons, the exact upper bound after 0 events, and power by simulation. `customer_minutes` takes an end time, so every arm of a comparison is measured over the same window. (ADR 0008, step 6)
- **The loop, watched.** `wyld3rness.loop.watch` wraps the loop's four ports, as tracing does, so every step of an incident is an event a viewer can show as it happens: the decision with its reason and the spend so far, the policy's answer, each action and each undo (told apart by order), each wait and each verdict. `EventLog` keeps one incident's events for a reader on another thread. Watching changes no answer, and no credential is ever an event. (ADR 0008, step 7)
- **Tracing.** Every run, eval case and command is an OpenTelemetry trace in a self-hosted Langfuse, with a span per step, eval scores on their case, and a cost on each model call from a committed reference price table. Export is batched on its own thread, so a slow or stopped backend does not slow a run. ([ADR 0007](docs/adr/0007-every-run-is-a-trace-in-a-self-hosted-backend.md))

### Example app: FindyFixy

- **Small model first.** A small model answers, and a larger one takes the case when the answer is invalid after one retry or its confidence is low. ([ADR 0001](docs/adr/0001-route-small-model-first.md))
- **Output contract and tools.** Every answer is a validated record with one retry that carries the validation error. Tool arguments are validated inside the tool, and the deploy tool runs both directly and over MCP. ([ADR 0002](docs/adr/0002-validate-outputs-and-tool-arguments.md))
- **Incident memory.** Synthetic past incidents are chunked, embedded and stored in Postgres with pgvector by an ingestion job that is safe to re-run. ([ADR 0003](docs/adr/0003-incident-memory-in-postgres.md))
- **Hybrid retrieval.** Keyword and vector search fused by reciprocal rank, then a cross-encoder reranker, returning incidents rather than chunks. ([ADR 0004](docs/adr/0004-hybrid-retrieval-with-reranker.md))
- **Console.** A local page that runs a triage or an eval and shows each step on the live architecture diagram.
- **On call.** `make oncall` runs seeded simprod storms through the harness's loop. FindyFixy's environment talks only to simprod's edge, as `X-Actor: findyfixy`, and computes each undo from the gateway's settings before the action; its decider asks the small model for 1 or 2 typed actions as constrained JSON, validates them, and retries once with the error. The storm driver is the controls' own, split so every arm shares one warm, inject, measure and clear sequence. `llm.ollama_reply` is now the one structured model call, used by triage and the decider. (research log, entry 013)
- **On call under a policy and a budget.** FindyFixy's rules: a rate cap only on a key sending at least 5% of the customers' request rate now, a restart only alone. Each decider call reserves its worst case on a $0.005 incident budget and has its reply capped at 400 tokens; the prompt states the rules from the same table the check enforces. `llm.ollama_reply` takes an optional output cap; triage's calls are unchanged. The prompt asks for one action by default and a second only if one alone cannot end the failures: asked for "1 or 2", the small model always proposed two. (research log, entry 014)
- **The agent and the loop in their own containers.** The agent is a small service that gets the metrics and returns a proposal; it holds no socket and no keys and shares no network with simprod (probed: edge and vault blocked). The loop handles each incident the host sends, with its own scraper, the policy, the signer and the edge; the host runs the storm and keeps its own verdict. `make oncall-up` builds one 69 MB image without the new `triage` extra (torch, Postgres, LangGraph, MCP), which local environments install with `uv sync --all-packages --all-extras`. Each undo now comes from the service's own answer (the value it replaced), with a settings read before the action as the fallback: under load the separate read failed and left the loop without an undo. (research log, entry 016)
- **The injection suite.** `make injection` plants 20 attacks, each a valid account key, in the busiest-keys metric the agent reads, and runs them through a fully fooled fake and the real model in the agent's container; an attack succeeds if an action it chose runs. Two rules close what an attacker could ask for: a restart only for a service that fails its health check, and backoff only turned on. (research log, entries 017 and 018)
- **On-call incidents in Langfuse.** The loop container traces each incident live, named for its arm, with the project keys `make oncall-up` puts in a private file; the agent gets none. Each run's trace id is saved in its record. (ADR 0008, step 6)
- **The console shows a storm.** The console drives one storm on simprod (choose the kind and who proposes: the model loop, the model with one try, or the script) and shows each try as it happens: a chart of customers' failures each second with every action and undo marked, a row per try with the proposal, the model's reason, the policy's answer, the actions, the verdict and the spend, and the schematic's loop boxes lit. It can also replay any saved run of the experiment or `make oncall` from its record. The loop container keeps each incident's events and serves them at `GET /incident/events`; the storm driver reports its phases and each second of customers; the model decider reports the incident's spend with each decision. A live storm cannot be stopped from the console, because only the loop may put back what is in force. (ADR 0008, step 7)
- **The experiment.** `make experiment` runs 24 held-out storms each through nobody, a script with no model, the model with one try and the model loop, in an order drawn per storm, all through the same loop container and measured over the same 240 s; `make experiment-power` prints the power table its N comes from; `make experiment-analyze` recomputes every number from a saved file. The loop container runs FindyFixy's script (`oncall/script.py`: backoff, cap the busiest key, both) when an incident asks for it, and takes the number of tries per incident. The model loop lost to the script. (research log, entries 019 and 020)
- **Nothing that kills an unattended run.** With one model configured, an answer still invalid after its retry is a typed `TriageError`, recorded by the eval, the console and `make triage`, which goes on to the next question. A query that loses its database connection reconnects with backoff for up to 60 s and retries, and logs both events. The database container runs an init process as PID 1, so an orphaned health check can no longer make Postgres restart itself. (research log, entry 004)

### Simulated production: simprod

- **Three services under real load, open to inspection.** A gateway writes each payment to a 4-shard ledger with fixed capacity per shard, with retries that fire at once as shipped, then notifies; an open-loop generator sends Poisson arrivals and counts latency from the scheduled time. Every service serves health, Prometheus-text metrics, an OpenAPI spec and JSON logs; the service that executes an action logs it with its actor. The services sit on a Docker network with no route out; an edge proxy publishes an allow-list on 127.0.0.1:8100 and never forwards the fault controls. Three typed actions: retry backoff with jitter and a retry budget, a per-key rate cap, each with an undo, and a restart with none. Standard library only, read-only and unprivileged containers. `make sim-up`, `make load-test`, inspection guide in `code/examples/simprod/README.md`. (research log, entry 006)
- **Seeded storms and their controls.** Three storm kinds from two faults, each with one fix that is a set of actions: a retry storm (a ledger slowdown that immediate retries keep alive; fix: backoff), a hot shard (a runaway client on one key, against a gateway deployed with backoff; fix: cap that key) and a compound storm (the same runaway against the gateway as shipped; fix: cap and backoff together). A chaos container injects them from inside the network; a customers service sends the same customers all the time and holds the runaway on its sealed port; a checker judges recovery only from what customers saw, each second over the 5 s ending at it. `make controls-pilot` sets the wait and hold windows from data, and `make controls` runs 21 storms under nobody, the scripted fix and a wrong fix that must be undone; a run that cannot be judged gets one more try. All 63 runs met their bar. `GATEWAY_BACKOFF` sets how the gateway is deployed. (research log, entries 008, 011 and 012)
- **Every action needs a credential.** The gateway, the ledger and notifications check `X-Action-Token` before any action: OpenBao verifies the signature, and the action, arguments, expiry and one-time id must match. Anything else is refused with 403 and its reason, logged with the actor; an action that runs is logged with its credential's id. The edge forwards the header. `make sim-up` runs OpenBao as a server with in-memory storage, initialises and unseals it through the API (not dev mode, which prints its root token and unseal key to the log), and writes its keys and a sign-only and a verify-only pass to the git-ignored .bao folder; `simprod-vault check` runs before every experiment and stops it on an expired pass, a sealed vault or a clock skew. The controls sign their scripted and wrong-fix actions the same way. (research log, entry 015)
- **Open-file limit raised to 65,536 in every simprod container.** At the default 1,024, a burst after a 2 s stall of the customers took the gateway past the limit, every new ledger connection failed at once, and the gateway never recovered, even with the right fix in force. (research log, entry 009)

### Tooling and security

- **The on-call image.** `findyfixy-oncall:local` builds on simprod's pinned and patched Python base and installs 47 locked packages with hashes. Grype v0.120.1: 0 Critical, 82 High, every one in Debian base packages with no fix available (55 Debian will not fix, 27 OpenSSL with no fix released), none in a Python package.

- **The privacy scanner catches this computer's names.** It reads the host name, and on macOS the computer and local host names, at every run, so a renamed computer is caught on the next commit; nothing about the machine is stored. Comments that described the development machine now state the project's memory requirement.

- **OpenBao for simprod's signing key.** OpenBao 2.7.2 pinned by digest, with zlib 1.4-r0 and OpenSSL 3.5.9-r1 installed at pinned versions: Grype v0.120.1 found 1 Critical and 21 High in the published image and 0 Critical and 13 High in ours. The 13 stay: 5 OpenSSL advisories with no fix yet (libssl3 and libcrypto3 each), go-jose v3 (no fix) and v4 (fixed in 4.1.6) and klauspost/compress (fixed in 1.20.2, in OpenBao 2.7.3), which are compiled into OpenBao and change only with an OpenBao release. OpenBao is reachable only on 127.0.0.1:8200 and simprod's internal network.

- **Decision diagrams.** `tools/diagram.py` draws each ADR decision picture from a spec file in `code/docs/adr/fig/`, with the live page's own Lucide icons; the console's page embeds a copy under "Where it runs", and `make check` fails if a picture or its copy differs from a fresh render. (ADR 0008, step 4)

- Locked dependencies with a 7-day release cooldown, `make audit` for known vulnerabilities and unexpected startup hooks, and container images pinned by digest and scanned with Grype before first use.
- simprod's base image, `python:3.13.18-slim-trixie` pinned by digest, scanned with Grype v0.120.1: no Critical, 84 High, of which 5 had a Debian fix (CVE-2026-85091 in zlib1g, CVE-2026-19499 and CVE-2026-5435 in libc6 and libc-bin). The image installs those fixes at pinned versions, whose changelogs are dated 2026-10-10 and 2026-11-01; the built image scans with 0 fixable High. The other 79 High matches (25 bugs: 8 in OpenSSL not yet fixed, 17 Debian will not fix) sit in code the services do not run: no TLS, no mount tools, no Perl.
- A privacy scanner in the pre-commit and pre-push hooks blocks personal data and secrets in files and commit metadata.
- Ruff and mypy in the hooks and in CI. CI runs with a read-only token and no secrets, with actions pinned by commit.
- `make check` covers documentation drift, the repository tools' tests and the privacy scan.
- The local Langfuse's ClickHouse no longer keeps its own profiler and internal logs (`code/infra/langfuse/clickhouse-logs.xml`); the query and part logs expire after a day. Left on, they used about 15 GB and kept the machine busy with nothing running.
- The design and the engineering strategy are one document, `code/docs/design.md`, and the engineering rules for contributors are in `CONTRIBUTING.md`.

### Known issues

- Linux installs pull PyTorch's GPU libraries although nothing uses a GPU, which slows CI. CPU-only wheels are planned with the service image.
- The model names come from an untracked `.env` file, so a model swap changes answers without failing CI. Only the judge is pinned, through the baseline.
- The stale-database check catches a changed embedding model name, not a new revision of the same model.
- The golden set is small and synthetic, and it has not yet exercised escalation.
- The judge can reject a claim its own context supports (ADR 0008), so a faithfulness score alone does not show a wrong answer.
- On some golden cases the judge writes four questions where response relevancy asks for three, on every run, so that metric fails there (research log, entry 003).
- The direct and MCP tool runs record tokens without a model name, so Langfuse puts no cost on those calls.
- Nothing enforces a cost limit. Cost is computed after the fact, on the trace.
